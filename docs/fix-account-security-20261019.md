# 账号安全修复与 Docker 升级说明

本次完成源码修复、前端构建、后端测试与 JAR 打包；未连接或部署生产服务器，线上生效需要更新部署。原审计和截图中的异常密钥属于事件证据，应保留记录。

## 修复结果

| 问题 | 修复后行为 |
| --- | --- |
| 登录可无限尝试 | 每 15 分钟单账号最多 20 次登录尝试，单 IP 最多 100 次；计数保存在 MySQL，跨实例、重启共享，超限返回 429。成功登录也计数，避免并发/重置计数绕过 |
| 改密后旧 JWT 仍有效 | 新增独立 `user.auth_version`，正常改密、找回密码、改绑邮箱、管理员设置密码/邮箱/角色、封禁/解封及服务端退出都会撤销旧会话；每次认证核对数据库版本。余额变动不影响会话 |
| 只有 JWT 就能改绑邮箱 | 改绑要求当前密码、原邮箱验证码和新邮箱验证码；验证码场景隔离，原邮箱地址由后端从当前账号读取；首次绑定无原邮箱的账户要求当前密码与新邮箱验证码 |
| 默认/弱 JWT 密钥 | 移除公开缺省值，取消短密钥补零；缺失、过短、重复字符弱值及常见示例值使启动失败；使用 `openssl rand -hex 32` 生成独立密钥 |
| 默认管理员密码 | 新建管理员必须指定至少 10 位的初始密码，不再使用 admin123；已有管理员密码保持数据库中的值，需自行检查并更换弱密码 |
| 验证码可能返回客户端 | 完全移除 devCode 返回路径，SMTP 关闭时拒绝发送；旧数据库里 dev_return_code=true 也不能返回验证码；邮件发送失败时撤销该验证码 |
| 重置密码暴露邮箱是否注册 | 先验证验证码，未知邮箱与错误验证码统一错误响应 |
| 管理员列表包含密码哈希 | User.password 禁止 JSON 序列化，会话版本也不返回客户端 |
| 截图中的 `*`、`default,pro`、`pro,image` 分组 | 创建/修改密钥仅接受一个数据库中存在且启用的分组。直接调用 API 同样校验；历史异常分组密钥在中转认证时返回 403，不会继续用于请求或计费 |
| 并发资料修改可能写回旧密码/余额 | 用户改密/改绑使用带原密码哈希和原邮箱条件的局部原子 SQL；管理员操作仅更新明确提交字段，不把整行旧快照写回；安全版本递增与改密/改绑在同一 SQL 中完成 |

新设密码统一至少 10 位，UTF-8 编码最多 72 字节，避免 BCrypt 截断；既有短密码仍可正常登录，但建议立即换为独立强密码。

登录、找回密码、正常改密、资料修改和新建中转密钥增加安全事件日志，记录结果、可用的用户/操作者 ID、来源 IP、UA，不记录密码、验证码、完整 JWT 或 API 密钥。找回密码日志不包含邮箱及目标用户 ID，应结合邮件服务记录关联。

退出登录向服务端请求撤销该账号全部网页会话，随后清理浏览器；请求网络失败时只能保证本机退出，必要时通过改密或管理员处置撤销服务端会话。

## 需要注意的行为变化

- **第一次更新后所有旧网页登录令牌失效，所有用户需要重新登录。** 旧令牌没有 authVersion，不兼容放行。多实例必须全部替换，不能继续将用户请求路由到旧版本。
- 密码与邮箱修改成功后，当前设备也需要重新登录。前端两个个人资料入口均已更新验证表单和跳转。
- 历史多分组/通配符/不存在/已停用分组的 API 密钥被拒绝。保存为有效单分组可恢复使用；**事发中创建的可疑密钥应禁用并轮换，不应因为修改了分组就重新信任**。
- 撤销网站会话不会自动停用独立的中转 API 密钥。攻击者创建的合法单分组密钥及可能被复制的原有密钥，需要单独禁用/轮换；本次没有删除线上密钥或改动生产记录。
- 验证码仍使用现有进程内存存储，多后端实例需要验证码请求粘性路由；重启会使待用验证码失效，需要重新发送。登录限流和会话撤销使用数据库，不依赖 Redis。
- 必须配置真实 SMTP 才能注册、找回密码或验证邮箱；不会通过调试模式绕过。
- 客户端 IP 使用服务端解析后的 remoteAddr，不直接读取用户提供的 X-Forwarded-For。保留仓库 Nginx 对转发头的覆盖规则，后端端口不直接暴露公网；使用 CDN/外层代理时需正确配置可信代理，否则限流可能按代理 IP 合并。

## Docker 升级

先备份数据库和事发日志，记录可疑密钥的 ID、预览、创建时间及用量，避免导出完整 token。更换部署前检查 `.env` 中 `JWT_SECRET` 是独立强随机值，初始管理员密码变量满足要求，并检查真实管理员密码和邮箱安全。

本次启动迁移会为已有 user 表增加 `auth_version BIGINT NOT NULL DEFAULT 0`，并创建 `auth_attempt_bucket`。迁移可重复运行；DB 用户需要相应 ALTER/CREATE 权限。`schema.sql` 同时提供兼容升级语句。无需删除或重建数据库卷。

**源码 Docker Compose 部署**：在包含本次源码的部署目录执行：

```bash
docker compose up -d --build --wait --wait-timeout 300 backend web
docker compose logs --since=10m backend
```

**预构建 Compose 部署**：将本次生成的 `dist/`、`backend/target/backend-0.0.1-SNAPSHOT.jar` 和最新 `backend/src/main/resources/db/schema.sql` 按已有预构建目录约定分别放到 `dist/`、`backend/app.jar`、`deploy/schema.sql`；再执行：

```bash
docker compose up -d --force-recreate --wait --wait-timeout 300 backend web
```

JAR 和 dist 必须一同更新；迁移在后端启动时应用。多实例应统一下线旧后端并更新，避免旧实例接受旧 JWT。首次部署的 MySQL 初始化脚本只在新卷执行，已有数据库依靠应用迁移。

如果启动被 JWT 密钥检查拒绝，设置新的随机密钥后重建 backend；不要恢复公开默认密钥或绕过检查。没有在本次输出或记录服务器的真实密钥。

升级后，用管理员确认：旧网页登录状态不能继续访问；用户重新登录正常；改密后旧设备会话失效；无法创建 `*` 或多个分组的密钥；正常单分组密钥可用；邮箱验证码发送和改绑流程正常。检查对外站点使用 HTTPS。
