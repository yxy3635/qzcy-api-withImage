## 更新已有中转服务器

以下操作都在服务器原项目根目录（包含 `compose.yaml` 与现有 `.env`）执行。不要在新目录中启动第二套 Compose。先保留现有源码备份；跨版本后端更新也应按 `docker-deployment.md` 备份数据库和图片数据卷。

若你要更新这几次的全部改动，上传完整包，例如放在 `/tmp`，在原项目根目录解压：

```bash
unzip -o /tmp/imagecreater-update-full-20261013.zip -d . -x compose.yaml deploy/nginx.conf .env.example
```

包内文件直接位于项目根层，没有额外嵌套目录。这里保留服务器已有 Compose、Nginx 和环境配置示例，尤其避免覆盖你自己的域名、端口和可信代理配置；包本身不含实际 `.env`。如果当前 Compose/Dockerfile 配置与仓库差异很大，应先比较配置再构建。本次新增标签和缓存计费不需要修改这些配置。

如果只更新本次前端标签，改用：

```bash
unzip -o /tmp/imagecreater-compaction-label-20261013.zip -d .
```

## 分别构建和更新前后端

当前仓库 Compose 服务名：后端 `backend`，前端 `web`。先检查现有配置：

```bash
docker compose config --quiet
```

后端（包含缓存计费更新；启动时自动补充缺失字段）：

```bash
docker compose build backend
docker compose up -d --no-deps --wait --wait-timeout 300 backend
docker compose logs --tail=100 backend
```

前端（包含用户和管理员标签）：

```bash
docker compose build web
docker compose up -d --no-deps --wait --wait-timeout 120 web
```

检查：

```bash
docker compose ps
docker compose logs --tail=50 web
```

上述 `--no-deps` 适用于 mysql/redis 已运行的现有部署，不用于首次安装。它不会更新或重建数据库服务。若前述后端更新已经上线、此次只更新标签，只执行前端命令即可。完整包同时更新时建议先后端、再前端。

保留 `.env` 和原 Compose 项目名；不要执行 `docker compose down -v`。仅执行 `docker compose restart` 不会把新源码构建成新镜像。已有数据库无需重跑整份 schema.sql；后端自动迁移需要数据库账号具备修改本库表结构的权限。检查后端日志确认启动和迁移成功。

若曾自定义项目名，继续使用原来的 `docker compose -p 原项目名 ...` 或原启动方式，避免切换数据卷。

## 独立 Docker 构建命令

如果只需要构建镜像、稍后由自定义部署配置使用，可在项目根目录执行：

```bash
docker build -t imagecreater-backend:20261013 -f backend/Dockerfile backend
docker build -t imagecreater-web:20261013 -f Dockerfile .
```

这两条只构建镜像；仓库的 Compose 没有引用这些手动标签，因此它们不会自行更新现有容器。使用仓库默认部署时，优先执行上一节 Compose 命令。

## 更新号池

将 `workbuddy2api-messages-fix.zip` 上传号池服务器并解压至临时目录：

```bash
mkdir -p /tmp/workbuddy-messages-fix
unzip -o /tmp/workbuddy2api-messages-fix.zip -d /tmp/workbuddy-messages-fix
python3 /tmp/workbuddy-messages-fix/apply_messages_fix.py /www/wwwroot/workbuddy2api
```

最后一个参数替换为服务器实际号池项目根目录。脚本会在写入前检查版本、备份两个修改文件，支持重复执行。随后用原进程管理器重启；若号池使用 Docker，则按该服务器原来的 Compose 文件和服务重新构建。详细步骤见号池包内 `MESSAGES_FIX.md`。
